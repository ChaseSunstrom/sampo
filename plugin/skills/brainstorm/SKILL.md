# Sampo: brainstorm

Open-ended requests get ideas from several independent angles before any planning, so the work isn't limited to whatever comes to mind first. State changes go through `sampo`.

1. **Classify and capture.** Say "Treating this as open-ended: brainstorming first." `sampo capture "<verbatim request>" --type RESEARCH --tier M`, then `sampo focus` it. A sweeping request meant to keep standing ("keep improving it", "limitless", a date): also `sampo mandate set "<verbatim request>" --until <the end the user named>` (none named: set none), so sampo scout, sampo night and later sessions keep working under it.
2. **Context pack**: `sampo mission --request "<verbatim request>"` writes it under `research/` with the mission (pillars for a complete pass), the lenses the project's surfaces call for and the exact `sampo ideas` line; add to the pack what it can't know (≤ 1,200 words in all; the brainstormers see only this):
   the user's words verbatim and any CONTEXT/MUST/NEVER lines · what the project is (README's first paragraphs) · stack and entry points · top-level tree (depth 2, trimmed) · last 10 commits · test/build status (run them) · open Sampo queue and inbox titles (`sampo state`) · known limitations, TODO/FIXME counts, recent failures (`sampo log`/ledger) · constraints (budget, what must not change).
3. **Fan out**: `sampo ideas --pack <file> [--lens L ...]` runs one sub-agent per lens in parallel, each a fresh `claude -p` session with no tools and no MCP servers (a Claude Code subagent can't be tool-less; the pack is their shared, prompt-cached system text, and the run reports the cache tokens), and saves each answer under the project's `research/brainstorm-<time>/`. Lenses (default eight: user value, unspoken needs, delight, capability map, approaches, reliability, simplicity, bold bets; add `performance` or `security and safety` when the request is about them). A broad request with a concrete target ("a ton of benchmarks", "interop with no caveats") runs just `--lens 'capability map' --lens approaches` before its plan, so the plan covers the whole space, not the first items that come to mind. For an exhaustive or "cover everything" request add `--lens grid`: it crosses the request's surfaces with its actors and failure modes and asks for one idea per cell, naming the empty cells. The user's own recent requests and corrections are added to every pack automatically; so are the asks the user had to make that no earlier brainstorm predicted (with a `blind spots` lens that turns each into the question that would have caught it) and the `Next question:` lines earlier runs left, so each brainstorm improves the next; ideas come tagged by category, and `--deepen K` adds a yes-and round on the K biggest categories (use `--deepen 3` for anything open-ended). Prompt: `references/ideas-prompt.md`.
   **Super mode** ("fully featured", "everything", "all possible features", or the prompt note says so): `sampo ideas --pack <file> --rounds 4` runs rounds that each see every idea so far and add only new ones (gaps, second-order improvements, combinations), stopping early when a round adds fewer than 3. Read the deduplicated index `ideas.md`, not every lens file. Every idea that survives grounding becomes a brief (not just a slate); build them in rounds, and after each build round super-brainstorm the improved project again with `--seen <each earlier ideas.md>` (so it goes past them) until a run comes back dry. Dry means grounded yield, not zero titles (lenses always produce some): when fewer than about three new ideas of real value survive grounding, record it with `sampo decide` and stop; a cheap probe (two lenses, `--rounds 2`) is enough to tell.
4. **Merge, cluster, ground — all of it.** Dedupe across lenses, then cluster the ideas into capabilities (one line each: the capability and the idea titles in it). Ground every cluster, never a hand-picked shortlist: a grep or read per cluster, or one `sampo:fm-recon` per area in parallel for a big catalogue. An idea marked `near T-…` in ideas.md shares most of its words with that finished task, so check that task first. Ground against MASTER.md first (the system map names most features), then the code with three phrasings of the idea's nouns, and the verbs' own argparse help strings: "new" only when all three come back empty, and only after a canary: the same tool and scope finds a term known to be there (T-2674: an empty search proves nothing if it couldn't find anything); each "new" verdict records it as `canary: <term> found`. The canary is a built feature near the idea (its nouns or its module), never a term any search finds: Mission 7 met the rule with `def main` on 156 of 169 verdicts (T-2686), and `sampo research add` now warns when one term covers most of a catalogue's canaries. Then spot-check two of the grounded "new" or "partial" items yourself before any is built (T-2659: three of four from one pass were already built, missed by a single grep). Already done → mark done; premise false → mark why; unclear → note it. Brainstormers never saw the code, so nothing goes forward ungrounded — and nothing is dropped silently (T-0364: 400 ideas became 17 rows and the rest vanished; the user asked to see every idea before any was turned down).
5. **Score** each grounded cluster: value 1–5, effort S/M/L, risk low/med/high, confidence, and your mark — build, or skip with its reason. Slate = the build marks in value-for-effort order: a normal brainstorm defaults to ≤ 8 items (at most one L); super mode, or a user who wants "most of them", gets every cluster not marked skip, built in rounds. Security findings and baseline-breaking bugs go first.
6. **Record.** `sampo research add brainstorm-<date>` with the whole catalogue: every cluster, its ideas and lenses, grounding, score and mark. Turn the slate into briefs with one `sampo intake` block (tags, `CONTEXT:` lines from the pack); the rest go to the inbox (`sampo capture --source followup`).
7. **Show the catalogue, then go.** The user sees every cluster with your mark, not only the slate: a checklist page (Artifact) when it's long, so they can tick what to add or veto. Standard: ask one yes/no for the slate with that page. Full (`sampo autonomy` says full): record the choice with `sampo decide`, start the queue (`/sampo:next`), and put the page's link in the final report; the user's ticks later re-order the queue.
8. Close the brainstorm task with its Decision (`sampo task set ID --section Decision --text "<the slate and why>"`; it lands in decisions.md), a `self` audit (`sampo task audit ID self …`) and `sampo task done`.
